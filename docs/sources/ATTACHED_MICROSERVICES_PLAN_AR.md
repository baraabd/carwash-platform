أعدت التحقق من مستودعك، وما زالت النسخة المرجعية على `develop` هي `66e6d936`. سأعاملها مصدرًا لإعادة الاستخدام، وليس مستودعًا نغيّر نشاطه أو نشارك قاعدة بياناته مع المشروع الجديد.

# 1. القرار الأساسي: ماذا سنبني؟

المنتج المقترح يتكون من **ثلاث واجهات**: تطبيق العميل، وتطبيق فريق الغسيل، ولوحة الإدارة. وخلفها خدمات مستقلة تتواصل من خلال واجهات محددة وأحداث موثقة.

سأستخدم `carwash-platform` اسمًا تقنيًا مؤقتًا للمستودع؛ ليس قرارًا بشأن الاسم التجاري.

وبالنسبة إلى نموذج العمل، أبني الخطة الأولى على **شركة تدير فرق الغسيل وعربات التشغيل**، مع قابلية إضافة شركات أو مقدمي خدمة مستقلين لاحقًا. هذا افتراض تصميمي أولي، وليس قرارًا سابقًا مؤكدًا منك.

مع هذا النموذج، تكون رحلة العميل:

**السيارة ← الباقة والإضافات ← الموقع ← الموعد ← مراجعة السعر والدفع ← تأكيد الحجز.**

لن نفرض على كل عميل نشر طلب وانتظار عروض، كما يحدث في سوق الخدمات المنزلية. يمكن الاحتفاظ بمنطق العروض لاحقًا لعقود الأساطيل أو نموذج سوق الشركات، لكنه ليس شرطًا لحجز غسلة عادية.

**أما واجهة غسيل السيارات الحالية، فلا أعتبرها مستبدلة بهذه الحزمة.** لم أقرأ كودها في هذه الجولة، وبالتالي ما أعددته هو أساس مستقل يمكن ربطها به بعد مراجعة مساراتها وعقود بياناتها.

# 2. ما المقصود بـMicroservices في مشروعنا؟

لن يكون الاستقلال مجرد وجود عشرة مجلدات.

كل خدمة ستمتلك منطقها، وبياناتها، وواجهاتها، وترحيلاتها، وهوية تشغيلها، واختباراتها، وإصدار نشرها. وأي خدمة أخرى ستتعامل معها عبر عقد، لا عبر قراءة جداولها مباشرة. هذا هو مبدأ استقلال بيانات الخدمة، بخلاف وضع عدة تطبيقات فوق قاعدة أعمال مشتركة. ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/architect-microservice-container-applications/data-sovereignty-per-microservice "https://learn.microsoft.com/en-us/dotnet/architecture/microservices/architect-microservice-container-applications/data-sovereignty-per-microservice"))

سنحتفظ بـ**Monorepo** لتنظيم الكود، لكنه لن يعني **Monolith**:

| العنصرقرار المشروع |                                                       |
| ------------------ | ----------------------------------------------------- |
| المستودع           | مستودع موحد لتسهيل التطوير ومشاركة الأدوات            |
| تشغيل الخدمات      | عمليات مستقلة                                         |
| بناء الخدمات       | بناء مستقل لكل خدمة                                   |
| النشر              | يمكن نشر خدمة دون إلزام الجميع بالنشر                 |
| البيانات           | قاعدة منطقية وحساب وصول خاص بكل خدمة                  |
| المشاركة           | عقود خارجية ومكونات واجهة وأدوات تقنية فقط            |
| الممنوع            | مشاركة Prisma Client للأعمال أو استيراد كود خدمة أخرى |

يمكن أن تبدأ قواعد الخدمات على **خادم PostgreSQL واحد** لتقليل التعقيد التشغيلي، لكن بصلاحيات منفصلة. ذلك لا يوفر توافرًا عاليًا؛ فهو يبقى نقطة فشل مشتركة.

**Microservices هنا اختيار للاستقلال والتنظيم والتوسع الانتقائي، وليس وعدًا بأن التطبيق سيصبح أسرع أو أرخص تلقائيًا.**

# 3. الخدمات المستقلة التي نعتمدها

أقترح الحدود التالية للمنتج المستهدف. سننفذها تدريجيًا، وليس كل وظائفها في أول سبرنت.

| الخدمةالوظائف التي تملكها  |                                                                                          |
| -------------------------- | ---------------------------------------------------------------------------------------- |
| **Identity Service**       | التسجيل والدخول، OTP، الجلسات، كلمات المرور، الأدوار والصلاحيات ودعوات الإدارة           |
| **Customer Service**       | ملف العميل، سياراته ولوحاتها، عناوينه، تفضيلاته وموافقاته                                |
| **Catalog Service**        | باقات الغسيل، الإضافات، المدد، توافق الخدمة مع السيارة، إصدارات الأسعار وعروض الأسعار    |
| **Workforce Service**      | العامل أو الشريك، الفرق، عربات التشغيل، المعدات، المناوبات، التوثيق وإذن العمل           |
| **Booking Service**        | الحجز، سعة المواعيد، حجز الموارد، التوزيع، الإسناد، التنفيذ، الإلغاء وإعادة الجدولة      |
| **Billing Service**        | المدفوعات، النقد، الإيصالات، الاستردادات، دفتر القيود، اشتراكات العملاء واستحقاق الغسلات |
| **Media Service**          | رفع الملفات، تصنيفها، الحجر والفحص، القراءة المصرح بها، الاحتفاظ والحذف                  |
| **Communications Service** | الإشعارات، محاولات التسليم، محادثات الحجوزات، حالة القراءة والتحديثات اللحظية            |
| **Support Service**        | الشكاوى والنزاعات والأدلة وقرارات المعالجة                                               |
| **Reporting Service**      | مؤشرات الإدارة ونسخ القراءة والبحث في سجلات التدقيق                                      |

وتوجد **API Gateway** بوصفها بوابة تقنية إضافية: توجيه الطلبات، وتجميع بيانات العرض، وضبط بعض الحدود، وتتبع الطلبات. لكنها **ليست مالكة للحجوزات أو المال أو سياسات الأعمال**.

## لماذا أبقي الحجز والجدولة والتوزيع معًا؟

لأن إنشاء حجز يجب أن يحجز **الفريق والعربة والنافذة الزمنية** بشكل متسق. فصل هذه العملية منذ البداية على عدة قواعد بيانات يزيد حالات التعويض والتعارض.

لذلك ستكون `booking-service` خدمة مستقلة، وداخلها وحدات واضحة للحجز والسعة والتوزيع. **لا يلزم تحويل كل وحدة داخل الخدمة إلى Microservice أخرى.**

## أين ستذهب وظائف الأدمن؟

الأدمن واجهة لإرسال الأوامر إلى أصحابها:

الموافقة على العامل إلى Workforce، وتعليق حسابه إلى Identity، وتعديل الباقة إلى Catalog، ورد مبلغ إلى Billing.

**لن ننشئ خدمة أدمن واسعة تملك حق الكتابة في قواعد جميع الخدمات.**

# 4. ماذا نأخذ من تطبيق الخدمات المنزلية؟

نأخذ الوظائف والأنماط المناسبة، مع تغيير ملكيتها أو قواعدها عند الحاجة.

| الموجود في المشروع السابققرار النقل |                                                        |
| ----------------------------------- | ------------------------------------------------------ |
| الحسابات والجلسات وOTP              | إعادة الاستخدام بعد تكييف التصريح والتوقيع بين الخدمات |
| الملفات الشخصية والعناوين           | نقلها إلى Customer وإضافة السيارات                     |
| كتالوج الخدمات                      | تحويله إلى باقات وإضافات ومدد وأسعار                   |
| الطلبات والحجوزات                   | تكييفها للحجز المباشر وسعة الموارد                     |
| عروض المهنيين                       | خارج المسار الأساسي؛ امتداد اختياري لاحقًا             |
| رحلة تسجيل المهني                   | إعادة استخدامها للشركاء، وتبسيطها للموظفين المدعوين    |
| التحقق من الهوية                    | قراراته في Workforce، وملفاته في Media                 |
| مراجعات الأدمن                      | نقلها كأوامر إلى الخدمات المالكة                       |
| المحادثات والإشعارات                | تجميعها أولًا في Communications                        |
| سجل التدقيق                         | تسجيل محلي لدى صاحب القرار، ونسخة بحث لدى Reporting    |
| المحفظة القديمة                     | لا تُنقل باعتبارها نظام تحويل أموال                    |
| العقود المشتركة                     | إعادة تقسيمها إلى عقود صغيرة بحسب المجال               |
| قاعدة Prisma المشتركة               | **لا تُنقل بهذا الشكل إلى Microservices**              |

ملفات الحزم الحالية تؤكد وجود أساس React/NestJS والمكتبات المساندة، لكن ذلك لا يجعل كل ميزة جاهزة للنقل دون اختبار. كذلك وثيقة Money تصرّح بأن أجزاء التنفيذ والربط والأدلة النهائية غير مكتملة؛ فلا نعتمدها كنظام دفع حي.

## التغيير الضروري في Node.js

للمشروع الجديد نعتمد **Node 24 LTS** بدل نسخ Node 20 من المشروع القديم؛ صفحة Node الرسمية تُظهر أن Node 20 انتهى دعمه، بينما Node 24 ضمن LTS. ([nodejs.org](https://nodejs.org/en/about/previous-releases "Node.js — Node.js Releases"))

أما الإصدارات النهائية لبقية المكتبات، فتُثبت بعد اختبار التوافق وإنشاء Lockfile حقيقي. لن نحدّث React أو Prisma أو React Leaflet بصورة منفردة ثم نفترض توافق بقية المنظومة.

## إضافات يحتاجها الفصل

سنضيف **RabbitMQ** للأحداث التجارية، وعقود OpenAPI وAsyncAPI، وOpenTelemetry لتتبع الطلب بين الخدمات، وآليات Outbox/Inbox، وهوية وصلاحيات لكل خدمة.

NestJS يوفر دعم RabbitMQ، ويبين استخدام `@nestjs/microservices` مع `amqplib` و`amqp-connection-manager` والتأكيد اليدوي للرسائل. ([NestJS Dokumentation](https://docs.nestjs.com/microservices/rabbitmq "https://docs.nestjs.com/microservices/rabbitmq"))

لن نضيف MongoDB أو Kafka أو Kubernetes لمجرد وجودها ضمن الخيارات التقنية. ولا نحتاج محركي شرائح أو نظامي تصميم متنافسين للوظيفة نفسها.

# 6. الاتصال والأحداث: الجزء الذي يجب بناؤه بدقة

سيكون **HTTP** مناسبًا للطلبات التي تحتاج استجابة مباشرة، بينما تُستخدم **RabbitMQ** للأحداث، مثل:

`booking.confirmed.v1`، و`payment.verified.v1`، و`operator.suspended.v1`، و`media.scan-completed.v1`.

لكل حدث معرف وإصدار ومصدر ومعرف ارتباط، وللمستهلك قواعد واضحة للتعامل مع التكرار والترتيب.

## كيف نمنع فقد الحدث أو تكرار أثره؟

نعتمد التصميم الآتي:

داخل خدمة المرسل، تُحفظ العملية وسجل **Outbox** في معاملة واحدة. بعد ذلك ينشر العامل الحدث، ويتحقق من تأكيد الوسيط، ثم يسجل نجاح النشر.

داخل المستهلك، يُحفظ معرف الحدث في **Inbox** مع التغييرات المحلية في معاملة واحدة، ثم يُرسل ACK. إذا أعيد الحدث، يمنع القيد الفريد تنفيذ الأثر المحلي مرة أخرى.

**الضمان المستهدف هو at-least-once مع منع تكرار الأثر، وليس exactly-once شاملًا.** توثيق RabbitMQ يميز بين تأكيد الناشر وتأكيد المستهلك، ويوضح احتمالات إعادة التسليم بعد الفشل. ([RabbitMQ](https://www.rabbitmq.com/docs/reliability "https://www.rabbitmq.com/docs/reliability"))

وسننشئ **طابورًا لكل خدمة مشتركة في الحدث**. لا نضع الإشعارات والتقارير في طابور واحد ثم نتوقع وصول كل رسالة إلى الاثنين؛ مشاركة الطابور تكون بين نسخ المستهلك نفسه لتوزيع العمل.

أما البريد أو الدفع لدى مزود خارجي، فيحتاجان أيضًا مفاتيح منع تكرار أو مطابقة؛ فمعاملة قاعدة بياناتنا لا تمنع وحدها تكرار أثر خارجي.

# 7. الحجز وسعة المواعيد والعمليات الموزعة

هذه أهم قواعد المنتج المقترحة.

**Catalog** تنشئ عرض سعر ثابتًا له صلاحية وإصدار. يرسل العميل `quoteId`، لا مبلغًا يختاره من المتصفح.

**Booking** تتحقق من بيانات الحجز، وتحجز الفريق والعربة معًا، وتثبت لقطة السعر والخدمة والعنوان.

**Billing** تتعامل مع حالة الدفع، التي تبقى منفصلة عن حالة تنفيذ الغسيل.

في الدفع النقدي، يمكن أن يكون الحجز مؤكدًا والدفع غير محصل بعد. وفي الدفع الإلكتروني، لا تتحول عودة العميل إلى صفحة نجاح إلى إثبات دفع.

## ماذا يحدث إذا وصل الدفع بعد انتهاء مهلة الموعد؟

لا يجوز أن تؤكد المنظومة موعدًا أصبح مشغولًا.

لذلك نحتاج سير عملية محفوظًا — **Saga أو Process Manager** — داخل Booking. يعيد التحقق من السعة أو يطلب الإلغاء/الاسترداد من Billing، مع إظهار الحالة الحقيقية للعميل.

ولا يُحفظ هذا التسلسل في ذاكرة Gateway فقط؛ يجب أن يستمر بعد إعادة تشغيلها.

## كيف نمنع حجز المورد مرتين؟

ليس بإخفاء الموعد من الشاشة فقط، ولا بقفل Redis وحده.

نحتاج قيدًا في PostgreSQL يمنع تداخل النوافذ للفريق أو العربة نفسها، مع معاملة تحجز الموردين معًا. PostgreSQL يدعم نطاقات الوقت وقيود الاستبعاد المناسبة لهذا النوع من الضوابط. أرفقت مثال تصميم SQL، **لكنه لم يُنفذ أو يُختبر على قاعدة فعلية بعد**. ([PostgreSQL](https://www.postgresql.org/docs/current/rangetypes.html "https://www.postgresql.org/docs/current/rangetypes.html"))

وسنختبر أيضًا إعادة إرسال أمر الإنشاء بنفس `Idempotency-Key`: نفس المحتوى يعيد النتيجة السابقة، بينما تغيير المحتوى مع المفتاح نفسه يرفض بتعارض.

# 8. الحسابات والصلاحيات والأمان

سنحتفظ بمنطق التسجيل والجلسات وOTP وCSRF وتجزئة كلمات المرور، لكن الفصل يحتاج ضمانات إضافية.

## هوية المستخدم ليست هوية الخدمة

Identity وحدها ستملك مادة التوقيع الخاصة. بقية الخدمات تتحقق بالمفاتيح العامة، مع فحص مصدر الرمز وجمهوره وصلاحيته والخوارزمية وتدوير المفاتيح.

لن نوزع سر توقيع واحدًا على الجميع، ولن نثق برأس مثل `x-user-id` يرسله المتصفح. Gateway تزيل رؤوس الهوية الداخلية الواردة من الخارج، والخدمة المستقبلة تتحقق من هوية المتصل وتصريح العملية. الشبكة الداخلية وحدها ليست تصريحًا. ([OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/Microservices_Security_Cheat_Sheet.html "https://cheatsheetseries.owasp.org/cheatsheets/Microservices_Security_Cheat_Sheet.html"))

| الدورحدود صلاحياته |                                                |
| ------------------ | ---------------------------------------------- |
| العميل             | سياراته وعناوينه وحجوزاته فقط                  |
| العامل             | المهام المسندة إليه والبيانات اللازمة لتنفيذها |
| مسؤول التوزيع      | الجدولة والإسناد وإعادة التوزيع                |
| الدعم              | الشكاوى والتواصل ضمن نطاقه                     |
| مراجع التوثيق      | الوثائق والقرارات المصرح بها                   |
| المسؤول المالي     | التحصيل والمطابقة والاستردادات                 |
| مدير النظام        | إدارة الإعدادات والصلاحيات وفق السياسة         |

صلاحية دخول الأدمن لا تعني تلقائيًا الاطلاع على وثائق الهوية أو رد الأموال.

وللمتصفح نعتمد جلسة Cookies آمنة مع حماية CSRF، لا تخزين رموز الجلسة في `localStorage`. كما يجب أن يؤثر تعليق العامل أو إلغاء جلسته على العمليات الحساسة؛ لا نكتفي برمز قديم ما زال صالح التوقيع.

كل قرار حساس يُسجل في خدمة صاحبه ضمن المعاملة. Reporting يحتفظ بنسخة للبحث، لكنه ليس المكان الوحيد الذي يثبت حدوث القرار.

# 9. الصور والوثائق والخرائط والتحديثات اللحظية

## الصور والوثائق

**صور السيارات واللوحات والعناوين خاصة افتراضيًا.** لن ننقل سياسة وسائط عامة من المشروع السابق إلى صور العملاء دون مراجعة.

المسار المستهدف: تصريح رفع مرتبط بالمالك والغرض، ثم حجر، ثم تحقق من الحجم والنوع والمحتوى، ثم فحص، ثم اعتماد وربط بالسجل.

صور إثبات التنفيذ منفصلة عن الصور التسويقية. نشر صورة في معرض عام يحتاج مسارًا وموافقة مستقلين.

Workforce تقرر أهلية العامل، بينما Media تملك الملف وحالة فحصه وسياسة قراءته وحذفه. لا يعني نجاح رفع الملف أنه تحقق من الهوية.

## الخرائط

نعيد استخدام Leaflet وReact Leaflet وتجربة الدبوس وإذن الموقع، لكن نفصل بين **عرض الخريطة، وتحويل الإحداثيات إلى عنوان، وحساب الطريق**.

لن نعتبر Nominatim العامة خدمة غير محدودة. سياستها تضع قيودًا، ومنها حد إجمالي معلن يبلغ طلبًا واحدًا في الثانية؛ لذلك نحتاج مزودًا قابلًا للاستبدال وكاش وحدود استخدام مناسبة. ([OSMF Operations](https://operations.osmfoundation.org/policies/nominatim/ "https://operations.osmfoundation.org/policies/nominatim/"))

كما أن المسافة المباشرة ليست مدة القيادة.

التتبع المقترح للعامل يكون أثناء المهمة وبالغرض المطلوب، مع إظهار وقت آخر تحديث ودقته. لن نَعِد بتتبع خلفي مستمر من تطبيق ويب مغلق دون اختبار المنصة.

## التحديثات اللحظية

Socket.IO ستكون قناة لإبلاغ الواجهة بالتغير، وليست السجل الرئيسي للحجز.

عند إعادة الاتصال، تجلب الواجهة الحالة الحالية أو التحديثات منذ مؤشر معروف. فقد رسالة لحظية لا يجب أن يترك العميل على حالة خاطئة إلى الأبد.

أما SMS وPush وWhatsApp فتبقى موصلات تحتاج مزودًا وتهيئة واختبارات؛ ليست وظائف مفعلة في الحزمة الحالية.

# 12. الدفع والمحفظة والاشتراكات

سنفصل ثلاثة أشياء لا ينبغي خلطها:

**ثمن الغسلة، واشتراك العميل في غسلات أو مزايا، ومستحقات المنفذ.**

أما اشتراك المهني في المنصة، الذي ظهر في التأسيس السابق، فلا يُفرض على شركة تعمل بموظفيها.

## التصميم المالي

Billing ستكون مالكة حالة الدفع والقيود المالية. المبالغ أعداد صحيحة للوحدات الصغرى، باستخدام `BigInt` داخليًا وسلاسل عشرية في JSON. وتُحدد دقة العملة في إعداد معتمد، لا بافتراض منزلتين لكل العملات.

دفتر القيود ليس عمود `balance` نزيده وننقصه. نحتاج قيودًا متوازنة لكل عملة، ومراجع أعمال فريدة، وعدم تعديل القيد بعد ترحيله، وتصحيحه بقيود عكسية.

**النواة المرفقة تتحقق من التوازن فقط؛ لا تنفذ محاسبة أو تحصيلًا حقيقيًا.**

## تأكيد الدفع الإلكتروني

لا نثق بصفحة العودة أو صورة الإيصال وحدها. نتحقق من إشعار المزود وتوقيعه، والمرجع والمبلغ والعملة، ونعالج التكرار واختلاف ترتيب الأحداث. توثيق Stripe يبين هذه المتطلبات للـWebhooks؛ الاستشهاد به هنا لا يعني اعتماد Stripe أو تأكيد توفره لسوق المشروع. ([Stripe Docs](https://docs.stripe.com/webhooks "https://docs.stripe.com/webhooks"))

أي موصل محلي يبقى معطلًا إلى أن تتوفر وثائق API وترتيبات التاجر واختبارات فعلية. **وجود اسم شام كاش أو سيرياتل كاش في عقد قديم لا يثبت جاهزية الدمج.**

## اشتراكات العملاء

حجز موعد واستهلاك غسلة من الاشتراك عمليتان مختلفتان.

Billing تحجز الاستحقاق مؤقتًا، ثم تثبته أو تحرره وفق نتيجة الحجز. ويجب اختبار طلبين متزامنين يحاولان استهلاك الغسلة الأخيرة؛ لا يكفي قراءة العدد ثم إنقاصه لاحقًا.

# 13. طريقة كتابة الكود وربط الواجهة بالخادم

التنظيم المستهدف داخل كل خدمة:

```text
src/
  domain/           قواعد الأعمال الخالصة
  application/      حالات الاستخدام والمعاملات
  ports/            العقود التي تحتاجها الخدمة
  infrastructure/   قاعدة البيانات والوسيط والمزودون
  transport/        HTTP ومستهلكو الأحداث
```

ومسار الطلب:

```text
React Component
  → Query / Mutation Hook
  → Typed API Client
  → API Gateway
  → Controller + Validation + Authorization
  → Application Service
  → Repository / Transaction
  → قاعدة الخدمة
```

بعد الالتزام، تُرسل الأحداث من Outbox إلى المستهلكين.

نشارك **عقود النقل**، لا النماذج الداخلية كاملة. واجهة المستخدم لا تستورد Prisma، وخدمة Billing لا تستورد Repository الحجز، وخدمة Reporting لا تعدل حالة العملية الأصلية.

ولا نضع حدًا اعتباطيًا لعدد أسطر الملف باعتباره تعريفًا للنظافة. الفصل يكون بحسب المسؤولية، وقابلية الاختبار، والجهة التي تملك القرار.

# 14. التشغيل والمراقبة والاختبارات الآلية

## التشغيل والمراقبة

البداية المحلية عبر Docker Compose. لكل خدمة لاحقًا صورة مستقلة، وترحيل منفصل، وأسرار وصلاحيات خاصة.

في الإنتاج نحتاج TLS، وحجب المنافذ الداخلية، وصورًا مثبتة، ونسخًا احتياطية واختبار استعادة، وخطة تحديث وتراجع.

المراقبة المستهدفة: **Pino + OpenTelemetry + Prometheus + Grafana**، مع تخزين تتبعات وسجلات عند تجهيز التشغيل. OpenTelemetry يوثق أدوات Node للتتبع والقياسات؛ لكنه ليس منشورًا أو مفعّلًا في هذه الحزمة. ([OpenTelemetry](https://opentelemetry.io/docs/languages/js/getting-started/nodejs/ "https://opentelemetry.io/docs/languages/js/getting-started/nodejs/"))

سنراقب زمن الطلب والخطأ، وتأخر Outbox، ورسائل DLQ، وفشل فحص الملفات، والحجوزات المعلقة، وفروق الدفع، والتأخر في التنفيذ.

## الاختبارات المطلوبة

| الطبقةالبوابات |                                                        |
| -------------- | ------------------------------------------------------ |
| الكود          | TypeScript، ESLint، Prettier                           |
| الوحدات        | Jest أو Vitest بحسب الجزء                              |
| HTTP           | Supertest واختبارات التصريح والتحقق                    |
| البيانات       | PostgreSQL حقيقي، الترحيلات، Prisma Drift، عزل الأدوار |
| الرسائل        | RabbitMQ حقيقي، التكرار، الانقطاع، Outbox/Inbox        |
| الواجهة        | Playwright، حفظ حقيقي، RTL، التجاوب والوصول            |
| الأمن          | Dependency Audit، Gitleaks، Trivy، CodeQL، SBOM        |
| التشغيل        | بناء الصور، الجاهزية، الإيقاف الآمن، الاستعادة         |

الاختبارات الحاسمة تشمل حجز المورد نفسه بالتزامن، وتكرار أمر الإنشاء، ووصول الدفع بعد انتهاء الحجز المؤقت، وسقوط المستهلك بعد الالتزام وقبل ACK، وتعليق العامل قبل بدء المهمة.

**اختبار ببيانات Mock لا يثبت حفظًا حقيقيًا، ونجاح بناء صورة لا يثبت سلامة رحلة العميل.**

**حدود بيئة الفحص:** نجحت الترجمة والاختبارات على Node `22.16.0` وTypeScript `5.8.3` المتاحين هنا. هدف المشروع Node 24 وTypeScript 5.9.3 لم يُختبر بعد. تعذر تنزيل الاعتمادات من بيئة التنفيذ، ولم يكن Docker متاحًا؛ لذلك لم أعتبر قوالب NestJS مبنية أو شغالة.

القوالب تعيد نجاح فحص الحياة فقط، بينما تعيد الجاهزية **503 عمدًا**؛ حتى لا يظهر جزء غير منفذ باعتباره جاهزًا للإنتاج.

```powershell
node --test tests/domain.test.mjs tests/boundaries.test.mjs
node scripts/check-boundaries.mjs
```

هذه الأوامر تختبر النواة فقط، ولا تشغل التطبيق.
