## Cash and noncash journeys

1. Pricing (B) supplies a current authorized quote with exact money/currency/scale policy, catalogue and price revisions and expiry. Scheduling (C) owns the bounded hold; Booking (C) records immutable snapshots and durable compensation. Real Aleppo zones/hours/travel margins must come from A/owners, never Damascus/Riyadh coordinates or sample `SEEDS` values.
2. Guest booking consumes E's future scoped guest capability. Optional plate remains optional: absent plate must not block task identification, media authorization or handover. Personal contact/vehicle/place data is exposed only to authorized active assignment participants and approved financial/support purposes.
3. Dispatch assigns only current Workforce-eligible resources against valid Scheduling commitments. Acceptance, route, arrival, before-evidence, checklist, after-evidence and handover are distinct server facts. A readiness switch or stopped timer is not eligibility, arrival proof or completion proof.
4. For cash after washing, Work result/handover remains separate from Billing's cash receipt. Collector submits the server obligation's amount/currency, not a client recomputation; same-key replay and concurrent retries return one receipt. Complete-but-uncollected work stays in follow-up. Later collection requires approved historical collector authorization, not a permanently reused old assignment grant.
5. A receipt creates a tracked custody obligation for the approved holder. Prototype evidence supports field **team/operator custody and company settlement**: technician totals are explicitly customer order value, not earnings, and admin `wallets` displays work-team custody, settled and pending delivery. Individual vs team account holder, recipient/verifier, hold purpose, adjustment authority and custody limits are still C-D07 decisions for B/owner. No customer wallet top-up/withdrawal, payroll, provider payout plans or recurring debit is authorized.
6. Cash handed over by a holder is a delivery request. B's server verification and audit establish company acceptance, discrepancies and settlement. Work cannot be reopened/marked unpaid just by changing a local collection filter. Wallet, if approved, holds/reconciles Billing references rather than duplicating postings.
7. ShamCash/Syriatel Cash states are read-only to technicians. Proof image, QR navigation, completed service or submitted follow-up never verifies payment. Billing must authorize and record server verification. A pending transfer must not silently demand cash or a duplicate transfer. Whether pending electronic payment permits work is an explicit conflict between customer and technician references, C-D06.

## Durable recovery and compensation proposal

| Failure window | Owner and required durable action | Non-negotiable acceptance |
| --- | --- | --- |
| Quote expires or hold acquisition loses last-slot race | Pricing refuses expired quote; Scheduling atomic capacity refusal; Booking records refusal and releases any obtained hold | No booking/charge from stale quote; real DB concurrent test |
| Hold acquired, Booking crashes before commit | Scheduling bounded hold expires; Booking persists recoverable attempt before cross-service command and reconciles same key | No orphan permanent capacity; ambiguous response resolved via operation status/replay |
| Booking commits but broker unavailable | Booking local outbox retries with same event ID; consumer inbox atomic with effect | Do not roll back a committed booking because a notification is late |
| Finance succeeds after capacity expiry | Booking does not resurrect slot; persisted policy-approved reacquire attempt or Billing void/refund request; unresolved outcome visible | Preserve capacity constraints; authorized money recovery, no automatic paid confirmation |
| Assignment revoked during work/photo upload | Dispatch publishes revision; Booking sensitive command rechecks current assignment; Media blocks stale finalization/read | No further unauthorized work/image access; active work exception decided explicitly |
| Scanner or finalizer unavailable | Media keeps quarantine/processing; deterministic retry; expiration cleanup for unused reservations | UI cannot treat local upload/HTTP success as usable before/after evidence |
| Work result committed; cash HTTP response lost | Billing idempotent collection receipt and query/replay; Work/payment facts stay separate | Exactly one business receipt/posting/custody effect under concurrent requests |
| Help/payment follow-up delivery fails | D owner persists request and delivery attempt; Booking does not pretend resolution | Expose pending/failed delivery and source freshness |
| Custody submission duplicated or acceptance response lost | B owns independent submit/accept/reconcile records and replay keys | One accepted custody movement; discrepancy not hidden as settled |
| Service grant revoked / privacy request / object retained for exception | Media revokes access and coordinates owner retention decision through request record | No global cross-owner delete, no invented finance retention; audit and backup lifecycle separately proven |

All owner commands need fingerprint canonicalization, terminal/nonterminal replay response, durable recovery deadline, key lifetime and error/timeout vocabulary published by E. Exact numeric timeouts, retention and privacy policies are outstanding inputs, not fixture defaults. Event envelopes follow accepted event-contract package shape; event names/new payloads remain proposals. Producers authenticate through broker scope, not an untrusted `producer` JSON field.
