## Source facts and constraints

- `architecture/service-catalog.json` names 19 owners. Identity owns accounts and grants; Workforce owns personnel, teams, vans, verification and work eligibility; Billing owns verified payment, refunds, cash custody and the ledger; Wallet must reference Billing postings rather than create a second ledger. Configuration owns versioned policies rather than live domain transaction state; Reporting owns projections rather than source decisions.
- `docs/ARCHITECTURE_AR.md` records company-employed teams as a planning assumption and leaves marketplace providers optional. Its early ten-service ownership table is historical: the current catalog separately assigns Vehicle, Pricing, Scheduling, Dispatch, Wallet, Subscription and Reviews. Resolve the catalog/history mismatch through E; never use it to move ownership into Admin or Gateway.
- `docs/F006_IDENTITY_RUNBOOK.md` requires an audited offline first-super-admin operation. Current public registration cannot choose roles. The current security foundation has seven role names, granular grants, email/password plus email OTP, account `authVersion`, sessions and local audit. It does not establish branch scope, a complete admin invitation flow, independent MFA, a protected last-admin policy or an implemented bootstrap command.
- The admin reference contains Riyadh, SAR, sample names, role counts, wallets and a `Card` booking row. These are prototype data. The customer design lock authorizes the cash / Sham Cash / Syriatel Cash presentation and treats all QR/provider success as illustrative until server verification and merchant setup exist.
- `docs/design/f010-reference-manifest.json` registers the customer, technician and admin HTML references. Preserve these bytes and layout. Recording a missing production state or a necessary localization decision does not approve a redesign.

## How a decision becomes accepted

Record `{decisionId, revision, status:'ACCEPTED', approvedBy, approvedAt, evidenceRef, exactAnswer, affectedContractIds, effectiveEnvironment}`. E then registers matching schemas, transport semantics and consumer versions. A product answer cannot by itself prove runtime verification or production readiness. A provider integration answer must be backed by reviewed provider/merchant documentation; a local prototype or a memory of a conversation is insufficient.

If an answer changes a previously accepted policy, publish a new decision revision and review affected consumers/migrations/rollback. Preserve previous decisions and source evidence. Acceptance tests reference the exact accepted revision, never this open register as authorization.
