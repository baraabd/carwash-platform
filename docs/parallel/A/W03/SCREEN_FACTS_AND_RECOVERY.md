## Invalidation and asynchronous boundary

Current draft has no quote, availability, hold, serviceability, server revision or transport outcome field. `selectVehicleType`, package/extras and place edits retain unrelated choices; local pricing recomputes but nothing invalidates capacity. Day selection alone clears slot. `draftWithCurrentSchedule` only resets a day outside the offered day set; an expired time on an otherwise valid day is caught on submit/entry/confirmation. No interval refreshes an idle screen when time passes; actions/render boundaries re-read the clock.

For production, invalidate by the **published dependency inputs**, without blanket loss of typed contact/notes/save preferences. Vehicle/care/extras/location/time changes must make every affected old quote/eligibility/availability/hold unusable until refreshed; material price or slot changes require explicit reconfirmation. Opening/closing an edit without a material change must follow accepted dependency/equality policy rather than automatically destroying all facts.

The existing [draftFingerprint](https://github.com/baraabd/carwash-platform/blob/82e7402ed9ab6cc4f565f423441cd0655f2d627a/apps/customer-web/src/state/bookingConfirmation.ts#L108) covers recorded draft values, but `draftGeneration` advances only after C014 success and its receipts keep only the last ten confirmations in memory. It supplies local stale-click/replay protection, **not asynchronous query generation or durable server idempotency**. A future client effect needs accepted principal scope + exact input/version + request generation; drop an answer if any no longer match. Abort is an optimization, not proof a mutation did not commit. Do not let a late quote/serviceability/availability response overwrite a newer edit or reinstall an old hold.

The existing asynchronous business-adjacent input is [AddressEditorForm.locate](https://github.com/baraabd/carwash-platform/blob/82e7402ed9ab6cc4f565f423441cd0655f2d627a/apps/customer-web/src/widgets/address-editor/AddressEditor.tsx#L102). It prompts only on a user tap, drops a callback after editor unmount and applies to latest temporary values. `locating` disables its button; no request-generation marker exists. A late in-range GPS outcome may update the current pin even if the user changed pin meanwhile, while preserving typed address. This mounted guard must not be mistaken for a server-response race solution. Animation/focus callbacks change presentation only. There are no real quote/hold/confirmation pending requests or transport retry mechanisms yet.

## Confirmation, optional saves and recovery

[confirmBooking](https://github.com/baraabd/carwash-platform/blob/82e7402ed9ab6cc4f565f423441cd0655f2d627a/apps/customer-web/src/state/bookingConfirmation.ts#L163) checks replay/fingerprint and prerequisites at one passed instant, computes fixture price, normalizes values, performs optional local garage/address saves, creates immutable `WG-SESSION-n` order/payment snapshots, resets draft to contact only, records receipt and routes cash to tracking/electronic to payment. Capacity-skipped optional saves show warnings while demo order succeeds. Preparation failure commits no order/save/reset. This is pure synchronous state; it cannot exhibit accepted-before-response-loss, network uncertainty, cross-tab/server duplication, compensation or reload recovery.

Production recovery concepts below require accepted wire/status/storage policy:

| Situation                                     | Required behavior; boundary                                                                                                                                                                                                                                                          |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Quote/hold expired or changed before submit   | Refuse old facts, preserve useful input, return to owning step and show new facts; require new explicit consent for material changes. No substitute slot or client amount.                                                                                                           |
| Submit in flight                              | Bind one stable idempotency identity to one immutable canonical submission snapshot; double activation reuses it. Disable/confine conflicting confirmation actions. New draft edits must not mutate that pending payload.                                                            |
| Response lost / abort / timeout               | Record and recover an **unknown outcome** through accepted principal-authorized lookup/replay. Do not infer failure or generate a new key. Reload must resume the same operation locator under real authority. Retention/key syntax/storage are release inputs, not prescribed here. |
| Durable accepted result                       | Read server booking/payment projection; clear only the submitted draft generation after known acceptance. A late acceptance must not erase a newer draft or expose prior principal data. Client route change is not proof of creation/payment.                                       |
| Definitive rejection / unauthorized reference | Preserve input and actionable error, invalidate affected server facts; no local fixture fallback or guessed reference. Corrected intent gets new identity only under the accepted lifecycle.                                                                                         |
| Optional vehicle/address save failure         | Booking result remains authoritative. Show independent failure, retain recoverable save intent/status/retry identity, and avoid duplicate save/booking. Do not re-submit Booking just to retry a saved-record mutation.                                                              |
| Distributed failure / capacity compensation   | Booking orchestrates durable reconciliation, Scheduling holds/releases, Billing obligation/reversal. A displays their accepted facts; it never compensates by editing peer state or announcing financial success. Late payment cannot resurrect expired capacity.                    |
