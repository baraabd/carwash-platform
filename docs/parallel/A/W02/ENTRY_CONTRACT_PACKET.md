## 3. Proposed common vocabulary / schema version

Proposed semantic API contracts: `customer.v1`, `vehicle.v1`, `geo.v1`, separate `identity.guest.v1`. The E-owned npm package version/export map remains **TBD**; no guessed package version is accepted. Paths below are proposals using catalog `/internal/v1/{owner}` and `/api/v1` roots. OpenAPI/AsyncAPI and runtime validators must be published together; HTTP descriptor status must distinguish proposed/contract-only from provider runtime acceptance.

```ts
// Illustrative contract vocabulary, not a package export.
type UUID = string; // validated UUID; propose UUIDv4 generation
// Avoid UUIDv7 adoption until Identity's current UUID[1-5] validator is reconciled.
type Revision = number; // positive safe integer; never rounded bigint
type UtcInstant = string; // exact YYYY-MM-DDTHH:mm:ss.sssZ
interface PrincipalRefV1 {
  kind: 'account' | 'guest';
  subjectId: UUID;
}
interface CustomerRefV1 {
  customerId: UUID;
  revision: Revision;
}
interface ObjectRefV1 {
  id: UUID;
  revision: Revision;
}
interface ContactV1 {
  name: string; // trim, 2..60 characters when booking requires it
  phone: string | null; // profile optional; booking non-null
  verification: 'unverified'; // W02 has no asserted phone verification
}
interface CoordinatesV1 {
  crs: 'EPSG:4326';
  longitude: string;
  latitude: string;
  // canonical decimal strings, finite, lon [-180,180], lat [-90,90],
  // precision limit proposed 6 decimal places; explicit publication decision
}
interface ErrorV1 {
  error: {
    code: string;
    message: string;
    requestId: UUID;
    correlationId: UUID;
    retryable: boolean;
    retryAfterMs?: number;
    details?: { field?: string; currentRevision?: Revision };
  };
}
```

- Domain IDs are server-generated opaque UUIDs. Identity `subjectId` and Customer `customerId` are distinct. No phone, license plate, address string or sequential demo `CAR/ADR/WG` ID becomes a globally trusted identifier. Unique Customer mapping on `(principalKind, subjectId)`; service ownership tables enforce one active owner relation per saved entity in this W02 model.
- Wire revisions begin at 1, monotonically advance with committed owner changes; `ETag`/`If-Match` (or a single exact `expectedRevision` field if E chooses it) is mandatory on update/archive. Choose one canonical mechanism at publication, not competing values. Archive leaves immutable historical Booking snapshots untouched. Stale revision returns conflict; never a last-write-wins overwrite.
- E must publish and test allowlisted query, precondition and response-header forwarding before consumers use cursor/market filters or the selected revision mechanism. Operation tables do not establish current Gateway support.
- List results `{items, nextCursor, asOf}` have opaque subject/filter-bound cursors and fixed order `(createdAt,id)`, proposed default 20/max 50. No arbitrary SQL/sort/filter expressions. Existing demo capacities 30 vehicles/20 addresses are reference limits, not proven production policy; preserve current UI, request explicit production limit and duplicate/upsert decision.
- Decimal/string wire types avoid float money and imprecise location parsing. Customer/Vehicle/Geo DTOs contain **no authoritative balances or prices**. Future price consumption requests compatibility with B's proposed `{amountMinor: decimal integer string, currency, currencyPolicyRevision}` plus `minorUnitExponent`; these are not accepted wire types. Currency scale/policy is a real owner input, not guessed from demo JS totals. Geo estimates use nonnegative integer seconds/metres and explicit dataset revision, not money or slot availability.
- Time instants canonical UTC; date-only local booking choices use exact `YYYY-MM-DD` with `Asia/Damascus`, explicit conversion and timezone policy. Browser local time never defines expiration. Expiry decisions use server time. W02 address/vehicle timestamps are owner mutation timestamps, not booking promises.
- Strict request keys and bounded payloads; distinguish omitted patch field from explicit null (clear). Name/phone/plate normalization is deterministic, locale-aware and server-validated; reject oversized input rather than silently truncating server data. UI can cap while typing without inventing server acceptance.
- Current approved phone rule accepts normalized 8–15 digits and optional `+`, with leading zeroes preserved, not verified E.164. Country normalization/phone verification remains decision-pending. Plate remains nullable/empty optional, normalized Arabic/English digits, 2–20 approved Latin/Arabic letters/digits/spaces/hyphens with at least one digit when present. A plate is descriptive metadata, not proof of legal title.

## 4. Actor and guest authentication proposal

**Recommended for decision:** Identity issues a signed guest session with stable opaque subject, separate `principalKind='guest'`, revocation/authVersion, audience and bounded lifetime. Customer may create a local profile for this principal through an explicit idempotent bootstrap; it does not manufacture an Identity user or session. Preserve no-password guest booking. Do not pretend the current Identity member/session schema already supports this.

Proposed E-owned operations:

- `POST /api/v1/auth/guest-sessions` → Identity `/internal/v1/identity/guest-sessions`: `{}` with preauth CSRF + abuse budgets; returns guest session view with secure HttpOnly credentials and `expiresAt`, not a bearer secret in JSON/localStorage. Create only an actual guest session; no booking/profile/notification.
- `GET /api/v1/auth/guest-session` and bounded refresh/authorize/revoke operations: shape `{principal:{kind:'guest',subjectId},sessionId,authVersion,permissions,expiresAt}`. Member Identity V1 continues to work; E chooses additive union/version strategy and tests old client parsing.
- Existing auth fields from the browser are untrusted. Gateway verifies pinned issuer/audience/algorithm/JWKS and current Identity authorization, strips spoofed actor headers and forwards accepted verifiable credentials. Owners verify token/current permission and enforce local object ownership themselves. Service identity and delegated end-user identity are distinct; accept only explicitly authenticated service clients/audience grants. Neither `producer` JSON nor `x-service-name` identifies a caller.
- Cookie writes use exact allowed Origin + signed CSRF bound by Identity; idempotency does not substitute for CSRF. Current revocation is checked for replay as well as new writes; expired/revoked sessions cannot retrieve cached PII results. Browser logout clears local app caches and revokes credential state without silently deleting Customer/Vehicle records.
- Proposed guest permissions limited to own profile/addresses/vehicles/quote/booking read/create as explicitly accepted; never technician/admin/finance powers. Guest lookup cannot enumerate member records; matching phone/name/plate cannot merge guests or grant access.
- Losing/expiring a guest credential yields AUTH_REQUIRED/GUEST_ACCESS_EXPIRED. Cross-device recovery, lifetime aligned with booked work, lost-session access, claiming/linking with account verification and orphan-data cleanup are **unresolved owner decisions before BASE_W02**. Same-session operation is not evidence of recovery or claim. Contact format or OTP port existence is not proof of phone ownership.
- Identity/current-authorize unavailable fails closed. Specify authorization freshness/revocation race policy with E: cross-service DBs cannot provide an atomic Identity+domain transaction. Do not claim an owner-local transaction makes remote revocation perfectly atomic; bounded authoritative prewrite checks and short authorization grants require an accepted security design and race tests.

Return principal linkage only to its owner/authorized internal resolver, not broad admin/public reads. English preference cannot invent approved English UI; acceptance/design remains pending.

Type mapping is the approved UI alphabet; live Catalog compatibility must bind an accepted vehicle-class mapping rather than invent new classes. Vehicle stores reusable descriptions; Booking stores historical vehicle snapshots.

Profile/bootstrap and vehicle creation cannot atomically commit across services. Vehicle validates an accepted Customer owner-resolution contract before committing its local ownership row; foreign IDs are references, not cross-DB foreign keys. Unavailable Customer/Identity means fail closed/no vehicle created. Lost response replays through Vehicle idempotency. Customer existence becoming archived concurrently needs accepted invalidation/revalidation semantics; a projected event is not sufficient current authorization for critical booking.

Serviceability response:
`{decision:'serviceable'|'outside-zone'|'indeterminate',zoneId:null|UUID,zoneRevision:null|Revision,datasetRevision:Revision,checkedAt:UtcInstant,expiresAt:UtcInstant,reason:'matched'|'outside'|'manual-location-unresolved'|'ambiguous-zone',normalizedLocation?:CoordinatesV1}`.
Successful decisions require an available approved dataset/policy revision. Dataset/policy/provider outages use the unavailable error contract, rather than returning a successful decision with nonexistent revision references.
Return `indeterminate` only as a successful business uncertainty, never hide timeout/provider outage as serviceable. Requesting an unavailable published dataset should return stable unavailable error with recoverable UI; Booking must reject pending/indeterminate confirmation. Overlapping/boundary polygons, point-on-edge choice, published zone priority, timezone and effective windows require deterministic accepted policy/tests. Do not invent precise Aleppo coverage/hours, road/time data, live map/geocoder provider or source permissions.

## 8. Minimum W02 operational lookup and beneficiary resolution

These are required narrow contracts, not a postponement of every admin consumer until W07:

- Customer internal `GET /internal/v1/customer/by-id/:id` (or exact request body) returns `{customerId,revision,status,principalKind,displayName,maskedContact}` to an authenticated operations/support/finance service acting with **purpose-specific** authorization. Every read is audited with actor, service, targetId, approved purpose, request/correlation IDs and time. No name/phone enumeration or full export.
- Read/resolve retries may append audit attempts under the accepted request/attempt identity policy. Audit deduplication never caches or bypasses fresh authorization; lookup has no business mutation even when an audit append is required.
- Customer internal `POST /internal/v1/customer/resolve-beneficiary` request `{customerId,expectedRevision?,purpose:'admin-booking'|'customer-wash-entitlement'|<accepted approved-holder-purpose>,operationRef}` returns `{customerId,revision,principalKind,status,eligible:boolean,reasonCode,checkedAt}`. It resolves the intended beneficiary for later admin manual booking, Subscription and approved Wallet operations, not a payment merchant recipient, bank account, wallet balance, entitlement amount or globally transferable identity. For admin-booking, independently verify the acting admin/service grant, operational scope and case/operation purpose against the beneficiary; the admin actor never becomes the customer owner. Revalidate guest eligibility and the beneficiary revision before Booking accepts the later command. This W02 resolver creates no booking, hold or financial posting. Holder types/purposes remain approved-owner input; do not hard-code unapproved customer stored value, provider subscription/payroll or recurring debit scope.
- Vehicle exact-ID read/ownership resolution for assigned work/admin case is limited to `{vehicleId,revision,customerId,type,maskedPlate,status}` unless current work authorization specifically requires plate. Customer contact unmask is a separate audited scope tied to booking/support case; permission to dispatch does not automatically reveal arbitrary customer phones.
- Proposed new permissions for E decision: `customer.lookup:operations`, `customer.contact.read:case`, `customer.beneficiary.resolve`, `vehicle.lookup:operations`, `geo.read:operations`; bind to narrowly accepted roles and purpose checks. A separate proposed `customer.beneficiary.resolve:admin-booking` grant and operational-scope policy must be accepted for manual booking. Existing `operations.dispatch`, `billing.read`, `support.cases.read` are **not automatically broadened**. Service-level allowlists also constrain internal resolvers; super-admin does not replace object purpose checks.
- Public admin gateway routes, response masking and exact admin controls need D/E design/authorization agreement. Request IDs and target exact IDs are enough for minimum technical contract; broader search by name/phone/plate, bulk pagination, edit, archive and Geo management remain W07.
- Pricing/Booking self-owner resolvers return required snapshots and revisions only; they do not reuse unrestricted admin endpoints. Finance cannot resolve a beneficiary by raw phone and silently attach funds. Existing `booking.confirmed.v1` has `customerId` only and is contract-only; Customer principal mapping must be accepted before a guest customerId is emitted by Booking.

## 9. Idempotency, errors, timeout, recovery and events

### Proposed idempotency decision table (E/owner acceptance required)

| Operation class                                                               | Scope / fingerprint                                                                                                                                                                                                                                                                                                     | Replay and lifetime proposal                                                                                                                          |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Customer bootstrap; self mutation; address CRUD/archive; Vehicle CRUD/archive | `(owner,verified principal kind+subject,operation v1,resource id when present,idempotency-key)`; recommend current Gateway key alphabet `[A-Za-z0-9_-]{16,128}`, not UUID-only; canonical normalized request plus expectedRevision/route/version; HMAC-SHA256 with owner secret to avoid free-text fingerprints in logs | 24-hour replayable committed result/status/reference proposed; 7-day minimal hashed tombstone proposed; both **TBD retention decision** before freeze |
| Provider/internal owner resolve reads                                         | Authenticated service+delegated principal+purpose; read only, no mutation idempotency required                                                                                                                                                                                                                          | No reusable authorization cache beyond accepted freshness budget; no client price/eligibility authority                                               |
| Geo serviceability/estimates                                                  | Deterministic normalized input/dataset revision/effective time; no save side effect                                                                                                                                                                                                                                     | Explicit short result validity; never replays old serviceability into Booking acceptance without current validation                                   |
| Future W03 Booking create                                                     | Booking coordinator own actor/key/business intent plus quote/slot/contact/vehicle/address revisions                                                                                                                                                                                                                     | Booking durable operation identity/replay policy is separate; cannot reuse a 24-hour A CRUD TTL for financial/capacity recovery                       |

- Store local idempotency row+business mutation in one transaction; include outbox records only where an accepted external event is required. Enforce a unique scope/key constraint and concurrent locking. First request claimed in-progress; same key/different canonical payload returns `IDEMPOTENCY_CONFLICT` without mutation, including when expectedRevision differs. Same key/same payload returns the exact committed response/status (or accepted minimized receipt), not recomputed current profile. Actor authorization/ownership is rechecked before replay. Changes in session credential do not change stable principal scope, but a different guest is a different actor.
- Fingerprint format/version/key identifier and retained-key or compatible rehash policy need acceptance before HMAC key rotation; identical replays must not become false payload conflicts. Never log canonical private requests or secrets. No inbox/outbox is added solely to satisfy a generic test row without an accepted external effect.
- Define canonicalization rules once (sorted object keys; nullable vs omitted preserved; allowed arrays ordered or explicitly set-normalized; Unicode normalization explicit; no silent arbitrary text trim; schema version included). Client must retain key across duplicate taps, network errors and restart; do not invent a new key after a timeout.
- Invalid requests/auth failures are rejected before claiming key. Revision conflict/business validation rejected outcomes must follow an explicit published policy (recommended persist deterministic terminal rejected outcomes once claimed, so replays do not unexpectedly succeed after data changes). Transient dependency failure before mutation does not become a misleading successful receipt.
- After replay TTL, a tombstone should return `IDEMPOTENCY_EXPIRED` with minimal operation/result resource reference when authorized, not perform another create with that key. After metadata expiry the server cannot promise de-duplication; choose long-lived create uniqueness/operation status policy, documented key-reuse prohibition and archive retention before production. A vague "24h" does not prove durable recovery forever. PII-bearing saved replay responses require retention/encryption/deletion decisions; final TTL cannot be frozen while privacy policy is pending.

### Error semantics

Use stable owner code + compatible Gateway coarse code; publication must define transport mapping and preserve safe owner details. Proposed statuses: 400 `REQUEST_INVALID/UNKNOWN_FIELD`; 401 `AUTH_REQUIRED/GUEST_ACCESS_EXPIRED`; 403 `AUTH_FORBIDDEN/AUTH_CSRF`; 404 `NOT_FOUND` for missing/not-owned; 409 `REVISION_CONFLICT/IDEMPOTENCY_CONFLICT/IDEMPOTENCY_EXPIRED/OWNER_ARCHIVED/LIMIT_REACHED`; 422 `VALIDATION_FAILED/LOCATION_UNRESOLVED`; 429 `RATE_LIMITED` with bounded Retry-After; 503 `AUTH_UNAVAILABLE/OWNER_UNAVAILABLE/GEO_DATASET_UNAVAILABLE`; 504 `UPSTREAM_TIMEOUT`. Field errors contain field IDs and fixed messages, not phone/address/plate, SQL, provider credentials, stack trace or spoofed upstream message.

Current Gateway error union/mapping lacks these rich owner codes; E must accept additive nested owner code/details or mapping before app consumers. A non-owned lookup must not differ from missing ID. No fallback saves, success toasts, serviceable result or permission grants on failure. Refetch/review conflict rather than overwriting typed edits; keep user draft unsent and explain retry.

### Timeout / recovery proposal

- Current gateway configured default upstream timeout is 3000ms (range 50–30000ms). Candidate A owner total request budget 2500ms with Identity dependency ≤750ms and read/resolve DB ≤750ms; measured in actual stack and adjusted/published by E, **not claims of performance or existing enforcement**. Geo provider external lookup requires an explicit budget within ingress budget or asynchronous resolution, never unbounded retry.
- GET/side-effect-free resolve may retry at most one transient attempt within original deadline with jitter; bounded mutation retry uses the same owner key, only after unknown outcome via operation status/replay. Gateway never retries writes under a new key. Business rejection is terminal, not transient.
- Lost response after DB commit: read/replay returns one committed resource. Crash before commit: transaction rolls back, key/retry can resume. Crash after commit before broker publish: outbox worker resumes; crash after consumer commit before ACK: Inbox dedup prevents duplicate effects. Backoff/DLQ/observability/replay permissions are E acceptance inputs; event retry does not resend user notifications uncontrolled.
- No distributed data save implied by booking: W03 Booking may contain valid one-time vehicle/location/contact snapshots even when customer opts out of saved records. Saving reusable Customer address and Vehicle records is independent, with explicit failure notice/outcome. Do not use cross-service writes as if atomic; any orchestrated required save has durable coordinator/recovery and no deletion of successfully saved user records as automatic compensation.
