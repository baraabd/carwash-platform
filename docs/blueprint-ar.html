1. القرار ونطاق البداية

نبدأ مشروعًا مستقلاً يعتمد على خبرة وكود وأنماط المشروع السابق، دون تعديل مستودع الخدمات المنزلية أو مشاركة قاعدة إنتاجه. نفرق بين ملكية الدومين، وملكية البيانات، وحدود النشر. المستودع الموحد ينظم العمل، لكنه لا يلزمنا بإطلاق جميع الخدمات معًا. لكل خدمة بناء مستقل وعقد خارجي وقاعدة منطقية وهوية تشغيل وترحيلات تخصها. هذه القواعد مستندة إلى مبدأ استقلال بيانات الخدمة [W2].

المؤكد من طلب المستخدم: منتج غسيل سيارات متنقل، واعتماد Microservices، وإعادة استخدام التقنيات المناسبة. السوق الذي ناقشه المستخدم سابقًا هو حلب، سوريا. أما نموذج الشركة المنفذة بفرقها فهو افتراض تخطيطي أولي، لا قرار سابق مؤكد للمستخدم. لذلك نعتمد الحجز المباشر للعمل اليومي، ونترك تعدد الشركات والعروض كامتداد لاحق لا كتعقيد مفروض على العميل من البداية. اسم المجلد ليس اسمًا تجاريًا ملزمًا. لا نُعيد بناء الواجهة الحالية عشوائيًا قبل قراءة مستودعها؛ كود واجهة غسيل السيارات الحالية لم يُتح هنا.

الواجهات المستهدفة: تطبيق عميل، تطبيق فريق التشغيل، ولوحة أدمن. كلها React/Vite في البداية، مع تجربة هاتف أولًا. تطبيق الهاتف الأصلي مشروع مستقل لاحقًا عند تثبيت متطلبات الخلفية والإشعارات والتتبع؛ React Web ليس React Native. لا يتضمن هذا التسليم تطبيق هاتف جاهزًا أو PWA مكتملة.

حالة الحزمة: تتضمن قرار البنية، وخريطة ملكية، وقوالب دخول NestJS، ونواة TypeScript محدودة مختبرة، وعقد حدث، وتكوين بنية تطوير. ليست منظومة تشغيلية. التفاصيل الدقيقة في VERIFICATION.md.

4. ما نحتفظ به وما نضيفه وما نؤجله

نحتفظ بالعائلات التقنية: TypeScript، Node.js، NestJS، React، Vite، React Router، Tailwind، TanStack Query، Axios، React Hook Form، Zod، Radix UI، PostgreSQL، Prisma، Redis، Socket.IO، S3، Argon2، Passport/JWT، Pino، prom-client، Docker، pnpm، Turborepo وأدوات الاختبار والفحص المذكورة في LIBRARY_ADOPTION_AR.md.

نضيف ما يتطلبه الفصل: RabbitMQ وسيطًا للأحداث التجارية؛ عقود أحداث وواجهات بإصدارات؛ OpenAPI وAsyncAPI؛ معرف ارتباط موحد؛ OpenTelemetry للتتبع بين الخدمات؛ Outbox وInbox؛ هوية خدمة وصلاحيات شبكة ورسائل؛ اختبارات توافق عقود واختبارات فشل موزع.

لا ننقل تلقائيًا: قاعدة Prisma مشتركة، مفتاح JWT سري واحد لدى الجميع، مكتبات واجهة متكررة، MongoDB بلا استخدام مثبت، بيانات تجريبية، قيود وصول في الواجهة فقط، صفوف دفع شكلية، أو كل الوحدات الإدارية إلى خدمة واسعة واحدة. لا نبدأ Kafka وRabbitMQ معًا، ولا Redis Pub/Sub كبديل لصندوق أحداث الأعمال، ولا Kubernetes أو Service Mesh كشرط لإثبات Microservices.

نختار Node 24 LTS للمشروع الجديد. صفحة Node الرسمية تُظهر Node 20 منتهي الدعم [W1]. لا ننسخ الإصدار القديم تلقائيًا. إصدارات React وPrisma وبقية الحزم تُقفل بعد مصفوفة توافق فعلية؛ الجرد القديم هو مصدر المرشحين، لا سجل اعتماد آمن للإنتاج. خصوصًا يجب اختبار توافق React مع React Leaflet وDay Picker وبقية الحزم ذات Peer Dependencies. النسخ الموجودة في قوالب Nest هي مرشحات مأخوذة من المصدر وليست مثبتة أو مفحوصة أمنيًا هنا.

5. قواعد بيانات مستقلة دون تضخيم تكلفة البداية

يمكن تشغيل عدة قواعد منطقية داخل خادم PostgreSQL واحد في التطوير أو البداية؛ الاستقلال المطلوب هو ملكية وعزل الصلاحيات والعقود، لا وجوب شراء عشرة خوادم. يبقى هذا الخادم نقطة فشل مشتركة حتى تتحسن بنية الاستضافة.

تمنع الصلاحيات خدمة Booking من الاتصال بقاعدة Billing. لا توجد علاقات Prisma أو SQL joins بين قواعد الخدمات. يُنقل المعرف فقط في العقد. تأخذ الخدمة لقطة من البيانات المطلوبة وقت العملية أو تقرأ عقدًا داخليًا مسموحًا، ولا تستورد جدول الجهة الأخرى.

لكل خدمة حساب Runtime محدود القراءة والكتابة، وحساب Migration مستقل. مخططها وترحيلاتها داخل مجلدها. التحديث يجمع schema والترحيل واختبار التطابق، ولا يستخدم db push أو reset على الإنتاج. تكوين التطوير في الحزمة يوضح هذا الفصل، لكنه لم يُختبر على PostgreSQL فعلي هنا.

اللقطات لها معنى محدد: سعر وعملة ووصف الباقة وقت الحجز تبقى ثابتة؛ حذف عنوان محفوظ أو تغيير اسم باقة لا يعيد كتابة التاريخ. وفي المقابل صلاحية العامل الحالية لا تُستمد من لقطة قديمة إلى الأبد. يملك كل نوع بيانات سياسة تحديث ومدة صلاحية واضحة.

6. كيف تتواصل الخدمات؟

طلبات القراءة والأوامر التي تحتاج ردًا فوريًا تستخدم HTTP داخليًا بعقود OpenAPI ومهل زمنية محددة. الأحداث تستخدم RabbitMQ. نستخدم NestJS مع @nestjs/microservices وموصل RabbitMQ، أو Adapter تقني منخفض المستوى عندما تتطلب إدارة الناشر مؤكد التسليم تحكمًا أوضح؛ الوثائق الرسمية تبين الموصل وamqplib وamqp-connection-manager والتأكيد اليدوي [W3].

رسائل الأعمال تنشر في Exchange دائم من نوع Topic، مع Queue مستقلة لكل خدمة مشتركة. لا نضع Notifications وReporting على الطابور نفسه ثم نتوقع أن يصلهما كل حدث؛ نسخ المستهلك نفسه فقط تشترك لتوزيع العمل.

لكل ناشر هوية وصلاحية نشر على نطاق أحداثه. لأن RabbitMQ ACL يحدد موارد Exchanges/Queues، ننفذ ملكية الناشر على Exchange مخصص أو Topic Authorization مناسبة، لا اعتمادًا على حقل producer داخل JSON. تحقق بنية الحدث ليس إثبات هوية مرسله.

مثال الحدث booking.confirmed.v1 يضم معرف الحدث، ونوعه وإصدار مخططه، والمنتج، والوقت، ومعرف ارتباط، وإصدار الحجز، ومعرفي الحجز والعميل. لا يضم كلمات مرور أو بطاقة مالية أو صورة هوية أو عنوانًا دقيقًا. حتى المعرفات المستعارة تبقى بيانات تحتاج حماية.

لا نستخدم Kafka في الإصدار الأول لعدم وجود مطلب موثق يفرض سجل بث كبيرًا. ولا نفرض gRPC على كل اتصال. يمكن إضافته بقرار لاحق عند وجود حاجة مقاسة. هذا اختيار تبسيط، لا حكم بأن التقنية الأخرى غير مناسبة دائمًا.

7. عدم فقد الأحداث وعدم تكرار الأثر

داخل خدمة المرسل تُكتب حالة الأعمال وسجل Outbox في المعاملة نفسها. عامل نشر يحجز الدفعات مع Lease، وينشر برسالة دائمة وPublisher Confirm، ويتحقق من وصولها إلى Queue متوقعة، ثم يحدّث السجل. فقد اتصال بعد نجاح النشر وقبل تحديث السجل قد يعيد الرسالة، وهو سلوك نتوقعه لا نخفيه.

في المستهلك، يوجد قيد فريد على (consumerName,eventId). إدخال Inbox وتعديل الحالة المحلية يقعان في معاملة واحدة. بعد الالتزام فقط يأتي ACK. عند فشل مؤقت نستخدم إعادة محاولة محدودة وتأخيرًا، ثم Dead Letter Queue وتنبيهًا وسير عمل إعادة تشغيل مُدقق. لا نستخدم nack(requeue=true) إلى ما لا نهاية.

الضمان المستهدف at-least-once مع منع تكرار الأثر داخل المعاملات. ليس ضمان exactly-once شاملًا. الأثر الخارجي مثل إرسال بريد أو استدعاء مزود دفع يحتاج هوية محاولة ومفتاح منع تكرار لدى المزود إن دعمه، أو مطابقة تعالج نافذة الانقطاع. توثيق RabbitMQ يوضح اختلاف تأكيد الناشر عن تأكيد المستهلك واحتمال التكرار بعد الفشل [W4].

الترتيب لا يُفترض عالميًا. Consumer يقارن إصدار Aggregate، ويكتشف الفجوات ويعيد المزامنة بدل تطبيق حدث قديم فوق حالة أحدث. تبقى إعادة تشغيل الأحداث قابلة للمراقبة ولا تعيد شحن العميل أو إرسال رسائل تجارية بلا ضابط.

8. رحلة الحجز والتعامل مع العمليات الموزعة

المسار المقترح: السيارة ← الباقة والإضافات ← المكان ← الموعد ← مراجعة السعر وطريقة الدفع ← تأكيد الخادم.

Catalog ينشئ Quote ثابتًا له مالك وعملة وإصدار أسعار وصلاحية. العميل يرسل quoteId لا سعرًا من اختياره. Booking يتحقق من ملكية السيارة والعنوان والخطة، ويثبت Snapshot. داخل معاملة واحدة تُحجز نافذة الفريق والعربة مع هوامش خدمة وتنقل. يكون الحجز أولًا PENDING_CONFIRMATION.

في الدفع النقدي يمكن تأكيد الموعد بعد نجاح سياسة الحجز مع بقاء الدفع UNPAID. وفي الدفع الإلكتروني يُنشأ طلب دفع لدى Billing، ويظل التأكيد معلقًا إلى وصول إثبات الخادم وتحقيق شرط السعة. نجاح صفحة الدفع ليس إثباتًا.

نسجل Saga أو Process Manager داخل Booking، لا في ذاكرة Gateway. تنتهي مهلة السعة بإجراء صريح. إذا وصلت نتيجة دفع ناجحة بعد انتهاء المهلة، لا نؤكد موعدًا أصبح غير متاح: نحاول وفق سياسة محددة إعادة حجز السعة أو نطلب إلغاء/استردادًا من Billing ونعرض REFUND_PENDING أو حالة مراجعة. لكل أمر تعويض مفتاح منع تكرار، وتسجل النتيجة والسبب والمهلة.

الرد على إعادة إرسال الأمر بنفس Idempotency-Key ونفس المحتوى يعيد النتيجة السابقة. نفس المفتاح بمحتوى مختلف يرفض بتعارض. المفتاح مرتبط بالمستخدم والعملية، ويُحفظ مع بصمة معيارية للمحتوى ونتيجة العملية، وتُختبر الطلبات المتوازية، وليس الضغط المتكرر يدويًا فقط.

الآلة الأولية في الكود تتحقق من الانتقالات وإصدار السجل فقط. لا تثبت الصلاحيات أو وجود السعة أو الدفع؛ تلك الشروط مسؤولية طبقة Application والمعاملات وتحتاج اختبارات تكامل.

9. سعة المواعيد والتوزيع

السعة ليست عدد حجوزات اليوم وحده. يجب مراعاة مدة الباقة والإضافات وفئة السيارة وموقعها والفريق والعربة والمناوبة وهوامش الطريق وتعطل الموارد. نبدأ بتوزيع يدوي مدعوم بالنظام، بدل ادعاء وجود تحسين مسارات ذكي غير مبني.

تملك Booking رزنامة الحجز الفعلية. Workforce تملك صلاحية العامل والمناوبات الأساسية والمعدات؛ تُنسخ التغييرات عبر عقود وأحداث بإصدار. عدم توافر مورد أو تعليق عامل يمنع الإسناد الجديد ويطلق مراجعة الأعمال القائمة. قبل الإسناد الفعلي نعيد التحقق من الأهلية الحساسة، ولا نكتفي بإسقاط بيانات قديم.

الحماية من التداخل يجب أن تكون داخل قاعدة البيانات. يوضح المثال docs/sql/booking-capacity.draft.sql استخدام tstzrange وExclusion Constraint بحيث لا تتداخل حجوزات الفريق نفسه أو العربة نفسها. PostgreSQL يدعم هذه الأنواع والقيود [W8]. المثال ليس ترحيلًا منفذًا، ولم تُثبت سباقات التزامن هنا.

لا نضع now() في Predicate للقيد. انتهاء المهلة يُكتب كتغير حالة صريح. العامل المتأخر قد يجعل السعة أقل مؤقتًا، لكنه لا يبيح ازدواج الحجز. لا يعتمد التأكيد على قفل Redis وحده. تخزن اللحظات في UTC، مع منطقة زمنية للسوق لعرض المواعيد وتفسير المناوبات والاشتراكات.

نحتفظ بمفاهيم الجلسات وOTP وArgon2 وCSRF وRoles/Permissions، ولكن نعيد توزيعها. Identity وحدها تملك مادة توقيع الرموز الخاصة. الخدمات تتحقق بالمفاتيح العامة المعلنة وتدعم تدوير المفاتيح، وتتحقق من المصدر والجمهور والصلاحية والخوارزمية. لا نوزع سر توقيع مشتركًا يسمح لأي خدمة منتحلة بإنشاء هويات للجميع.

للمتصفح نختار جلسة آمنة HttpOnly/Secure مع SameSite مناسب وطريقة CSRF مكتملة في البوابة. لا نخزن Access/Refresh tokens في localStorage. يزيل Gateway رؤوس هوية داخلية يرسلها العميل؛ لا نثق بـx-user-id أو دور قادم من المتصفح. بين الخدمات هوية تشغيل مستقلة ونطاق وصول محدد واتصال مشفر. عضوية شبكة داخلية وحدها ليست تصريحًا [W5].

الصلاحيات حسب العملية والملكية والفرع أو جهة التشغيل. أدوار أولية: العميل، العامل، الموزع، الدعم، مراجع التوثيق، المالي، ومدير النظام. الرد المالي يحتاج صلاحية Billing لا مجرد دخول الأدمن. المشرف العادي لا يقرأ كل وثائق الهوية. كل خدمة تعيد التحقق من قواعدها، ولا تعتمد على أن البوابة وافقت سابقًا.

نقل الطلبات أو الأموال أو قراءة الوثائق أو بدء عمل بعد تعليق العامل يتطلب قرارًا حديثًا. إبطال الجلسة وإلغاء الإذن لهما قناة أحداث مع فحوص مباشرة للعمليات الحساسة وسياسة واضحة لأي كاش. عند تعذر التحقق من تصريح حساس نرفضه مؤقتًا، ولا نقلب فشل التحقق إلى موافقة.

الوثائق والحسابات والأموال لها سجل تدقيق محلي ضمن المعاملة. Reporting يقرأ نسخة التدقيق للبحث؛ تعطل Reporting لا يمحو السجل الأصلي. نحتاج إدارة أسرار ومفاتيح، وحدود طلب حسب IP والحساب والعملية، وقيود أحجام الملفات وDTO، وحماية SSRF في الاستدعاءات الخارجية. قواعد هذه الخطة ليست شهادة امتثال قانوني أو تدقيق أمني منجز.

11. الصور والوثائق والخرائط والتواصل

الملفات

نعيد استخدام Storage Port مع S3-compatible وموصل تطوير. صور السيارات واللوحات والعناوين تكون خاصة افتراضيًا. نشر صور تسويقية منفصل عن صور إثبات تنفيذ الخدمة، وله موافقة مستقلة. لا تُنقل سياسة التخزين العام للطلبات القديمة إلى صور العملاء بلا مراجعة.

مسار الرفع: تصريح رفع محدود ومرتبط بالمالك والغرض ← تخزين حجر ← تحقق حجم وبصمة ومحتوى ← فحص برمجيات خبيثة ← معالجة صورة وإزالة بيانات EXIF المناسبة ← Finalize ← ربط بالحجز أو ملف العامل. يُمنع جعل URL قدمه العميل هو ملفًا موثوقًا. استخدام وثائق الهوية يكون عبر قراءة مصرح بها ومُدققة، بروابط قصيرة أو تمرير محمي حسب التصنيف، دون CDN عام.

قرارات KYC يملكها Workforce؛ Media تملك الملف وحالة الفحص فقط. نختبر انتهاء الموافقة وتقييد القراءة والحذف والنسخ الاحتياطية. لا نعتبر وجود ClamAV في الاعتمادات دليل تشغيل العامل أو سلامة كل ملف.

الخرائط

نعيد استخدام Leaflet/React Leaflet وتجربة الدبوس وإذن الموقع. مزود الخرائط ومزود Reverse Geocoding ومزود Routing ثلاثة أشياء مختلفة. نضع Provider Port قابلاً للاستبدال، وحدود استدعاء وكاش وعدم إرسال بيانات حساسة إلى خدمات عامة بلا أساس مناسب. Nominatim العامة لها قيود استخدام، ومنها حد إجمالي معلن يبلغ طلبًا واحدًا في الثانية، وليست مصدر Autocomplete مفتوحًا غير محدود [W7].

لا نطلب موقع العامل طوال اليوم. التتبع أثناء المهمة فقط وفق الإذن والغرض وسياسة الاحتفاظ. نعرض وقت آخر تحديث ودقته، ونتعامل مع انقطاع الشبكة. مدة القيادة ليست المسافة المستقيمة. لا نَعِد بتتبع خلفية في تطبيق ويب مقفل دون اختبار منصة الهاتف.

التواصل

Communications تحافظ على الرسائل وحالة القراءة والمشاركة. Socket.IO قناة تحديث سريعة وليست السجل الرئيسي للحجز. عند إعادة الاتصال نجلب Snapshot أو Events منذ Cursor معلوم. تحديث الواجهة وحده لا يعني حفظ المعاملة. Redis Adapter لا يحوّل أحداث الأعمال تلقائيًا إلى سجل دائم. Push/SMS/WhatsApp موصلات مستقبلية تتطلب اختيار مزود وتهيئة حقيقية؛ لا نعلن إرسالها في هذه الحزمة.

12. كيف يُكتب الكود؟

داخل الخدمة: domain للقواعد الخالصة، application لحالات الاستخدام والمعاملات، ports لتعريف ما تحتاجه، infrastructure لقاعدة البيانات والوسيط والمزودين، وtransport لمسارات HTTP ومستهلكي الرسائل. يختبر Domain دون Nest أو قاعدة بيانات، بينما تُختبر المعاملات والمستهلكات على خدمات فعلية.

مسار الواجهة: Page/Component ← Query/Mutation Hook ← Typed API Client ← Gateway ← Controller/DTO/Authorization ← Application Service ← Repository/Transaction ← قاعدة الخدمة. ينشر Outbox بعد ذلك، ثم تُحدّث Projection أو تُبث إشارة إعادة الجلب.

العقود المشتركة صغيرة ومجزأة حسب المجال وإصدارها. لا حزمة واحدة تستورد كل ORM وجميع نماذج الأعمال. الـUI لا يستورد Prisma. العقود تحدد حقول النقل، لا تعطي المستهلك حق استيراد المنطق الداخلي. يمكن مشاركة التهيئة التقنية والتتبع والخطأ الموحد والاختبارات وDesign Tokens. أي تعديل كاسر يمر بإصدار متوافق وخطة انتقال؛ مشاركة Monorepo لا تفرض تزامن نشر الجميع.

لا نحدد عدد أسطر سحريًا لملف نظيف. نفصل بحسب المسؤولية والاختبار والتغير. لا يتصل Component مباشرة بالقاعدة. لا تحسب الواجهة أهلية العمل أو تؤكد الدفع. ولا يُستخدم عدد الاختبارات كمقياس وحيد للاكتمال.

13. الواجهة والمكتبات وRadix

نحتفظ بـReact وVite وRouter وQuery وAxios وTailwind وReact Hook Form وZod. Design System جديد قابل لإعادة استخدام المكونات السابقة: Button, Field, Dialog, Sheet, StatusBanner, Money, VehicleCard, PackageCard, AddressPicker, SlotPicker, BookingTimeline, ErrorSummary, EmptyState, Skeleton, StickyActions.

تعتمد واجهات العميل والفريق والأدمن هذه الأسس مع كثافة وتخطيط يناسبان دورها. الألوان Typography والمسافات والحالات تكون Tokens. نستعمل Lucide ومصدرًا واحدًا للحركات، وSonner للتنبيه العابر؛ الأخطاء التي تحتاج تصحيحًا تبقى بجانب الحقل وليست Toast تختفي فقط.

قائمة Radix التفصيلية لكل الحزم الست والعشرين موجودة في ملحق المكتبات مع قرار نقل منفصل. نعتمد الحوار والتأكيد والاختيار والتبويبات والأفاتار والتلميحات وغيرها عندما يظهر استخدامها. Menubar وContext Menu وHover Card ليست شروطًا لنسخة العميل على الهاتف. لا نخلط MUI وRadix كمرجعين متنافسين للشاشة نفسها، ولا نثبت React Slick وEmbla للوظيفة ذاتها.

العربية والإنجليزية وRTL/LTR جزء من كل شريحة، لا مرحلة ترجمة في النهاية. نختبر 320 و390 و430 و768 و1024 و1440 بكسل، لوحة المفاتيح والتركيز وقارئ الشاشة والتباين وتقليل الحركة. يبقى إدخال المستخدم عند فشل الشبكة واضح الحالة، لكن بيانات حساسة لا تحفظ في تخزين متصفح دائم بلا تصميم خصوصية. لا نخزن HTML حساسًا في Service Worker Cache افتراضيًا.

15. الدفع والمحفظة والاشتراكات

نميز ثلاثة مجالات منتج: ثمن غسلة، اشتراك العميل بعدد غسلات أو مزايا، ومستحقات شركة/عامل. اشتراك مقدم الخدمة في المنصة لا يدخل النسخة الأولى إلا إذا اعتمد نموذج Marketplace. الأجر الوظيفي ليس بالضرورة Payout لمهني مستقل.

لا ننشئ عمود balance قابلًا للتعديل اليدوي كمصدر مالي وحيد. Billing تملك Ledger ودورة دفع منفصلة عن دورة الحجز. المبالغ أعداد صحيحة للوحدات الصغرى؛ BigInt داخليًا وسلاسل عشرية في JSON. تحدد العملة ودقة وحدتها في سجل إعداد معتمد، لا بافتراض منزلتين لكل عملة. تعكس الضرائب والفواتير إعدادًا يُراجع للسوق؛ نواة التسعير المرفقة لا تنفذ ضرائب أو قواعد محاسبية تشريعية.

قيد التوازن في الكود هو فحص أولي، لا نظام محاسبة مكتمل. قاعدة البيانات تحتاج فرض دفعات متوازنة وغير قابلة للتعديل بعد الترحيل، وحسابات صالحة لكل عملة، ومراجع فريدة للأثر التجاري، وعكس القيود بدل محوها. يجب اختبار استرداد جزئي وحالات الشبكة والتكرار.

في الدفع النقدي العامل يسجل الاستلام والإيصال؛ هذا لا يساوي تسليم النقد للشركة. يوجد Cash Custody وتسوية عهدة ومطابقة. وفي الدفع الإلكتروني لا نثق بالمتصفح أو صورة إيصال وحدها. نستقبل Webhook بتوقيع صحيح ونطابق المرجع والمبلغ والعملة والمالك، ونحفظ منع التكرار ونعالج اختلاف ترتيب الأحداث [W6].

StripeAdapter أو أي مزود محلي يبقى Disabled إلى توثيق API والتاجر والأهلية والاختبار. وجود اسم شام كاش أو سيرياتل في مشروع سابق ليس توثيقًا متاحًا لموصل جديد. لا توجد في هذا التقرير مصادقة على توفر مزود دفع في بلد أو قبول نشاط معين.

استهلاك غسلة اشتراك يتم بالحجز المؤقت للاستحقاق ثم Commit عند تحقق السياسة، أو Release عند الإلغاء؛ مفتاحه يضم الاشتراك والحجز. كل ذلك داخل Billing مع طلبات Saga قابلة للتكرار. يمنع ذلك قيام حجزين متزامنين باستهلاك الغسلة الأخيرة. التجديد والاشتراك المتكرر والحجز المتكرر عمليات مختلفة؛ التجديد لا يحجز موعدًا مشغولًا تلقائيًا.

16. التشغيل والمراقبة

تبدأ البيئة المحلية بـDocker Compose ومنصة بيانات معزولة عن المشروع القديم. الخدمة تُبنى في صورة مستقلة، ومعها عاملها وترحيلاتها وإعداداتها. تشغيل الخدمات على جهاز واحد لا يحولها إلى Monolith؛ الاعتماد المتبادل على قاعدة مشتركة أو إصدار موحد هو ما نمنعه. في المقابل الجهاز الواحد لا يعطي توافرًا عاليًا.

في الإنتاج نحتاج TLS، وعدم نشر المنافذ الداخلية، وحسابات خدمات، وأسرار خارج المستودع، وصور مثبتة بوسم غير قابل للتغير أو Digest، ونسخ احتياطية مشفرة واختبار استعادة. تغيرات المخطط تتبع Expand/Contract وخطة توافق رجوعي. توقف خدمة لا يطلق إعادة تشغيل متسلسلة لكل المنصة.

المراقبة المقترحة: Pino للسجلات، OpenTelemetry لتتبع الطلب/الحدث، Collector للتصدير، Prometheus للقياسات وGrafana للعرض، وTempo للتتبعات وLoki للسجلات عند تجهيز بيئة التشغيل. OpenTelemetry JS توثق تهيئة التتبع والقياسات لـNode [W9]. هذه منتجات مستهدفة، لا خدمات شغلت في الحزمة.

المؤشرات: زمن API ومعدل الخطأ، Connection Pool، عمر Outbox، عدد Retry/DLQ، تعطل فحص الملفات، التأخر في الوصول، حجوزات معلقة، فروق الدفع، وفشل تأكيد الاستحقاق. لا نجعل userId أو bookingId Labels ذات عدد غير محدود في Prometheus. يحتفظ Trace بالارتباط مع حجب البيانات الحساسة. نحدد ميزانية أداء وتوافر بعد قياس سيناريو الحمل المتوقع، لا بإعلان نسبة نجاح افتراضية.

/health/live يثبت حياة العملية. /health/ready يثبت جاهزية تلك الخدمة لاعتمادها المباشر ووظيفتها، وليس صحة كل خدمة في الشركة. قوالب هذه الحزمة تعيد 503 عمدًا لأنها غير منفذة وظيفيًا؛ لا تُغيرها إلى 200 لإجبار شاشة CI على النجاح.

17. الاختبارات والأمان الآلي

بوابات الدومين: الأنواع والتحليل والتنسيق والوحدات. بوابات التكامل: PostgreSQL حقيقي لكل مالك، حسابات الأدوار، Prisma drift، الترحيلات القديمة والجديدة، RabbitMQ الحقيقي، Outbox/Inbox، Webhooks تجريبية، وتوافق العقود. اختبارات HTTP منفصلة عن اختبارات المتصفح. أدوات Node test المستخدمة في هذه النواة لا تستبدل Jest/Supertest أو Vitest/Playwright في منظومة المنتج.

سيناريوهات لا يجوز إسقاطها: عميلان يحجزان الفريق والعربة في النافذة نفسها؛ إعادة إرسال أمر إنشاء؛ انتهاء Hold متزامن مع نجاح دفع؛ تكرار Webhook؛ سقوط المستهلك قبل/بعد Commit أو ACK؛ توقف الوسيط بعد Commit المرسل؛ فقد تحديث Socket وإعادة جلب الحالة؛ تعليق عامل قبل البدء؛ قراءة وثيقة من حساب غير مخول؛ استهلاك متزامن لآخر غسلة اشتراك؛ استعادة النسخ الاحتياطية.

بوابات UI: اختبار عميل/فريق/أدمن عبر API الحقيقي، حفظ وعودة وتسجيل دخول، RTL واستجابة والوصول، صور قبول بالنسخة نفسها. بيانات mock تفيد الوحدات ولا تثبت الحفظ الحقيقي.

بوابات الأمن: Dependency Audit وGitleaks وTrivy وCodeQL وSBOM وتحديثات Dependabot، مع مراجعة تراخيص الأصول والمكونات. لا نقبل استثناء أمني دائم بلا سبب ومالك وانتهاء. لا ننقل قائمة تجاهل الأسرار القديمة كاملة. لكل PR أدلة على SHA النهائي، وقواعد حماية تمنع الدمج عند فشل بوابة مطلوبة. النجاح الآلي ليس نشرًا؛ النشر عملية مع صلاحيات وخطة تراجع مستقلة.

19. قواعد التخطيط وكتابة طلبات التنفيذ
