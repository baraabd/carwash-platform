## 4. Security, Media and Workforce scenarios

### C-SEC-01 — verified principal, never command-selected actor

**Given** Identity sessions for OP-A and OP-B; only OP-A has the current assignment for BOOKING-A; and a separate service credential cannot impersonate a user. **When** OP-B submits a command body/query carrying OP-A's operator ID, or sends caller-selected `x-auth-subject`, role/permission headers, modified token claims, missing/expired/revoked session, or an alternate direct-service route. **Then** invalid authentication is rejected; an authenticated but unauthorized principal is denied; gateway forwarding cannot elevate it; the owning service binds the actor from independently trusted identity context and current object authority. No assignment/work/media/cash record, outbox effect or secret disclosure occurs. The audit distinguishes forged/denied attempts with no token or sensitive payload. Re-run the positive OP-A command to prove the route is functional and properly scoped, not merely absent.

The W02 executable subset, after E's real access provider, is only forged actor/self/case-binding authority against the narrow Workforce provider in C-WF-02. The BOOKING/ASSIGNMENT/WORK/cash portion above remains W03/W04 dependent; no guessed role header, Media stub or not-yet-implemented Booking authority closes it early.

Contract-specific HTTP status/error names remain proposals until publication: normally invalid authentication is 401 and authenticated forbidden access is 403; a private-resource 404 concealment policy needs consistent approval. Do not assert an invented endpoint/status as already accepted.

### C-SEC-02 — scoped, current document-review authority

**Given** a narrow real Workforce case/actor-binding provider is already accepted, real Media stores DOC-A bound to OP-A's case, and a reviewer has the accepted verification permission and object/case scope, while OP-A, a customer, an unscoped admin and a Billing reviewer lack review authority. **When** DOC-A is quarantined, pending scan, rejected, infected, revoked or unfinalized and any actor attempts preview/read/download or an evidence-dependent approval decision. **Then** no actor, including the authorized reviewer, obtains its content/read grant or approves eligibility from it. Approved rejection/correction actions may record the unavailable-evidence reason without reading unsafe bytes or treating it as clean; their exact contract is separate from a positive evidence-based decision.

**Given** DOC-A instead becomes clean, finalized, private and currently authorized under real Media. **When** each actor attempts preview/read/download, approve/reject/request-correction, link replacement or revision change. **Then** the currently scoped reviewer can read the permitted finalized evidence and make its permitted case decision. OP-A may read its own clean finalized document only through the separately accepted `SELF_VIEW` grant/object policy; missing `verification.review` denies review decisions, not every explicitly permitted owner self-read. The owner cannot use `SELF_VIEW` to approve/reject/request-correction or obtain another owner's/restricted object; unauthorized read grants/decisions receive the accepted denial without bytes, URLs or review mutation. Quarantine/unfinalized/rejected/revoked content remains unreadable to both reviewer and owner regardless of grant purpose. The authorized decision is version checked and audited by actor, subject, reason, prior/new revision and decision ID. Replaying the identical decision returns its accepted result; a conflicting/stale decision cannot overwrite the newer one. Role removal/session revocation prevents further decisions under the accepted revocation semantics. Document review does not grant financial approval; frontend visibility does not confer backend authority. This complete review/eligibility consumer is sequenced after Media; it is not a prerequisite for the narrow case-binding provider Media needs.

## 5. Cash and financial boundary scenarios

### C-FIN-01 — duplicate request yields one collection effect

**Given** WORK-A is service-complete/handoff, BOOKING-A uses cash, an exact Billing obligation is unpaid, and the currently authorized assigned OP-A submits its permitted collection claim with KEY-A/FP-A. **When** double-clicks, duplicate network delivery, a timeout retry and two independent concurrent HTTP connections send the same command. **Then** Billing's accepted scope binds the key to actor/operation/obligation and canonical semantic payload; one persisted collection effect, one command result and one local outbox event exist. Every successful replay returns the same stable accepted result without a second claim/ledger movement. Whether the first result means operator-claimed collection or verified collection follows B's policy; this case never labels a claim bank-reconciled or company-settled. The UI displays that exact server state and survives page/restart recovery. Database uniqueness and transaction evidence, not only client button disabling, must establish the invariant.

### C-FIN-02 — mismatch cannot alter amount or recipient

**Given** KEY-A was accepted for FP-A within the proposed namespace `(verified actor, operation, target obligation)`. **When** the same actor/operation/target reuses that key with a changed semantic payload inside that scope, such as amount/currency or an accepted mutable claim/destination field (FP-B). **Then** Billing rejects a fingerprint conflict and preserves the first immutable result/effect; no silent replay as if the altered request succeeded, no overwritten snapshot and no second movement. If a semantic destination is itself part of the accepted scope, move that variant to the separate namespace case rather than asserting a same-scope fingerprint conflict.

**Given** another actor, operation or target uses the same key string. **When** that new namespace command is submitted. **Then** independently test its authorization and business uniqueness: do not assume a conflict with KEY-A from a different namespace; unauthorized actor/target access is denied, and an authorized distinct namespace still cannot bypass the business constraint against duplicate collection/custody movement for the same obligation. Exact canonical money representation/currency exponent, field ordering/normalization, scope, key lifetime and namespace fields remain accepted contract inputs. Partial/over/under payment behavior remains blocked on C-D07; the prototype's full-amount demo rule is not production finance policy.

### C-FIN-03 — persisted recovery across crashes
